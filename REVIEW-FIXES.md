# Исправления по Windows-отчёту M2

Эти изменения включены в **0.2.1-m2** и **0.3.1-m3a**. Выберите одну ветку: 0.2.1 — без функций чтения документов, 0.3.1 — с уже добавленной M3a. Это альтернативные полные сборки, не два обязательных последовательных обновления.

## Статус внешней проверки

По переданному пользователем отчёту для **0.2.0-m2** подтверждены: доступ к старым проектам, реальный ответ B (`claude-haiku-5.5`), сохранение истории/usage/model, маршрут D (`anthropic/claude-opus-4.6`), статус limited, повторный запуск и расшифрование DPAPI, резервный ZIP. Это результаты проверки на стороне пользователя, не наше собственное выполнение Windows/API.

Пункт отмены с сохранением уже полученного текста **не считается закрытым**: в отчёте два отменённых ответа пусты. Само ожидание семь секунд и отсутствие usage не доказывают, что клиент получил текст. До первого текстового фрагмента возможны сетевое ожидание, обработка запроса и нетекстовые сообщения API. Usage нередко передаётся только при нормальном завершении, поэтому его отсутствие при отмене не означает отсутствия начислений.

## E1 — отмена и фрагмент

Причина именно наблюдавшихся пустых ответов пока **не установлена**. Потерю уже показанного текста в доступных тестах воспроизвести не удалось. Не заявляем «E1 полностью исправлена».

Внесены конкретные изменения:

- Если текст действительно получен, отмена должна сохранить его в БД с cancelled. Проверяется синхронизацией по полученному тексту, а не по задержке в секундах.
- Если первый текст не получен, сообщение прямо говорит об этом, вместо неверного «полученный фрагмент сохранён».
- Защищена запись от запоздавшего checkpoint: финальный статус не может снова стать running; более короткая запись не может затереть уже сохранённый префикс. Это устранение возможного сценария гонки, **не доказательство причины внешнего E1**.
- Под ответом и в SQLite сохраняются `streamDiagnostics`: число полученных символов, время до первого текста и длительность. Для настоящего адаптера дополнительно — число разобранных JSON-кадров и флаги известных вариантов формата.
- Содержимое reasoning, сырой поток, ключи и запросы в диагностику не записываются. Диагностика — метаданные ответа, не файл с секретами.

### Повторная локальная проверка

1. Сформулируйте задачу с достаточно длинным ответом.
2. **Дождитесь появления нескольких слов в интерфейсе**, а не только смены кнопки на «Остановить».
3. Нажмите «Остановить». После обновления страницы текст должен остаться и статус должен быть cancelled.
4. Отдельно проверьте отмену до первого текста: пустой ответ допустим, но он должен честно говорить «до получения первого текстового фрагмента» и показывать 0 символов.
5. Если уже видимый текст исчезнет — пункт всё ещё не пройден. Для диагностики достаточно модели, статуса, finishReason, значений `streamDiagnostics` и факта «текст был виден / не был виден». Не присылайте БД, резервную копию, ключ или текст конфиденциальной задачи.

## E2 — пустой ответ

Добавлена поддержка текстовых частей массива `delta.content` и полного `message.content` в потоковом кадре, когда до него текст ещё не поступал. Полный terminal message не добавляется повторно после уже полученных deltas. Reasoning не подменяет пользовательский ответ и не выводится.

Если завершённый поток по-прежнему не содержит поддерживаемого текста, остаётся `errorCode=empty`. Это не объявляется успешным ответом. Неподдержанный формат, нетекстовые данные и первый текст различаются в диагностике. Автоматического платного повтора нет. Доступа к исходному проблемному потоку нет, поэтому утверждать, что именно E2 пользователя устранена, нельзя.

## E3 — старые неуспешные задания в контексте

Подтверждено по коду: ранее пользовательский запрос после ошибки/отмены оставался в следующем контексте, хотя его ответ исключался. Теперь связанные запросы и ответы со статусом cancelled/error/interrupted/limited/running либо без завершённого ответа **целиком исключаются из последующих API-вызовов**. История на диске не удаляется. Полностью успешные пары передаются вместе; бюджет не оставляет ответ без исходного задания.

Исключение: заметки пользователя из M1 без requestId сохраняются как пользовательские заметки — их нельзя надёжно считать неудачными API-запросами. Приложение не переименовывает их в ошибки задним числом.

Количество исключённых неуспешных заданий видно под новым ответом. Новое правило применяется и к существующим обсуждениям: чистить базу не требуется. Детерминированная суммаризация не добавлялась и дополнительных платных вызовов нет. Поведение модели после очистки контекста всё равно не гарантируется. Для продолжения limited-ответа явно вставьте нужный фрагмент в новый запрос или повторите задачу с подходящим лимитом.

## Отдельный лимит D

В настройках добавлено поле **«Отдельный лимит D»** (`maxOutputTokensD`). Пусто — использовать прежний общий лимит. Можно явно установить 4000 (допустимо 128–8192), если это поддерживает модель/провайдер. B при этом остаётся на своём лимите.

**Автоматического повышения до 4000 нет**: это могло бы увеличить расходы без выбора пользователя. Достижение лимита не означает ошибку маршрутизации; статус limited сохраняется. Увеличение лимита не гарантирует завершения ответа и не отменяет ограничений провайдера.

## Установка

Сделайте резервный ZIP, остановите старую службу, распакуйте выбранную новую сборку в отдельную папку программы, выполните новые install.bat / start.bat. Рабочую папку и каталог конфигурации не удаляйте. Версия в `/api/health` должна стать **0.2.1-m2** либо **0.3.1-m3a** соответственно.

Модели, согласие, ключ и история сохраняются. Схема основной БД не меняется. Новые сведения пишутся в JSON сообщения; старые сообщения без диагностики не переписываются. Перед откатом используйте копию, сделанную до обновления.
