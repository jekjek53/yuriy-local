# Проверка 0.4.0-m3b

## Результат и среда

**Проверочная сборка, готова к локальной приёмке, но не объявлена принятой на Windows.**

- Linux, Python 3.13: `python -m pytest -q` → **110 passed, 3 skipped**, 1 прежнее предупреждение Starlette об AnyIO BlockingPortal; последний прогон 7.64 с.
- По сравнению с принятой базой 0.3.1 (93 passed) добавлено 17 серверных тестов M3b. Прежние тесты не заменены фиктивными результатами.
- Три Windows-only пропуска: DPAPI, junction и Job Object. Новые операции требуют отдельного Windows-прогона.
- Вызовы провайдера в автоматических проверках имитируются. Реальный SprutDock, расходы/качество C, сетевые задержки и Office на ноутбуке **не проверены**.
- Для python-docx 1.2.0/lxml 6.1.3 успешно скачаны совместимые wheels CPython 3.12/3.13 Windows x64. Проверена доступность файлов, не установка/исполнение на Windows.

## Новые серверные проверки

### Материалы

- TXT preview ничего не меняет; только отдельный confirm создаёт новую редакцию с новым ID и журналом.
- Скачивание «до»/«после», сохранение исходных байтов, страховочная копия, backup/restore истории.
- Ревизия, SHA, срок, архив, чужой проект и отказ backup блокируют правку.
- Подмена исходника во время backup блокируется повторной проверкой SHA.
- Отказ коммита/удаление плана не заменяют прежнюю текущую редакцию; повтор плана не применяется.
- DOCX: однозначная замена, сохранение остальных ZIP-частей и оформления run, таблица, отказ сложному документу/разбитой фразе/внешним relationships/некорректному XML.
- CRLF TXT и точные координаты выбранного C-фрагмента после нормализации textarea.

### DOCX

- Новый draft, предварительное скачивание, подтверждение/повтор, источники и metadata, TXT/DOCX, отказ подмене SHA.
- Сохранение артефакта при backup/restore; невозможность подделать серверные metadata обычным PUT.
- Квитанция confirmationId; автор/дата DOCX/пометка «ЧЕРНОВИК». Специальный обрыв HTTP после коммита не симулировался: серверная квитанция проверена, браузерный fallback реализован, но не объявлен отдельным пройденным fault-injection сценарием.

### C

- Включение/модель/лимит, связь с исходным ответом и scope, повтор requestId без нового вызова.
- Исходный вопрос и исторические цитаты, повторное согласие, отсутствие C в последующем обычном контексте.
- Подмена вопроса/отсутствие подтверждения отклоняются.
- Переполненный JSON-контекст отвергается до провайдера; частичный однозначный фрагмент проверяется с честным scope, без скрытой обрезки.
- Отмена/ошибка не превращаются в успех и не вызывают платный автоповтор.

## Воспроизведение

```text
python -m pip install -r requirements-dev.txt
python -m pytest -q
```

Для браузера нужен отдельно установленный Node/Playwright Chromium (не runtime-зависимость приложения). Запустите `tests.mock_server:factory` через uvicorn с `YURIY_TEST_RUNTIME` в **новой тестовой папке**, затем соответствующий `tests/ui_m*.cjs` с `YURIY_TEST_URL`. Не направляйте эти сценарии на рабочую службу: они меняют тестовое состояние и предполагают mock API. Для сценариев используйте отдельные чистые runtime-папки.
